In-app help system

Every screen carries a bottom icon bar that can show two help glyphs — a white live icon-legend overlay and a red per-screen help page — plus ℹ buttons on provider cards that deep-link to per-provider or per-repository pages. This is distinct from the bundled HTML documentation hub (this very page) reached from About.

The two help glyphs

BottomIconBar (ui/shared/SharedComponents.kt) can show up to two right-pinned glyphs, both defined in data/MetadataDefaults.kt (mi.helpLegend / mi.help):

❔ white — HELP_LEGEND
U+2754, renders white
Shows whenever the screen has at least one bar icon at all (useLegend = specs.isNotEmpty()) — no longer gated by topic id or icon count. Tapping it opens a full-screen live icon-legend overlay in place; it never navigates anywhere.
❓ red — HELP
U+2753, renders red — Android ignores tint on emoji, so the colour is the glyph's own
Always navigates to the screen's main help topic (help/{topicId}). Shown by default in the bottom bar; relocated to the persistent top Home bar in Home bar mode (Settings → UI tweaks → App home), where the bottom bar is rendered with suppressScreenTraceAndHelp = true. The white ❔ stays in the bottom bar in both modes.

The View family — report View screens, plus Model Info / provider / flock / swarm / HTML-preview view screens, all of which route through their own ViewBottomBar instead of the generic BottomIconBar — shows only the red ❓; the white ❔ was removed there.

Provider cards on Model Info / Trace detail / Costs carry a separate ℹ button that deep-links to a per-provider or per-repository help page (see below) — a third, unrelated mechanism from the bottom-bar pair above.

Help-home reference topics

All live in GlossaryHelp.kt's glossaryHelp map: help_about, help_getting_started, concepts, help_glossary (with sub-pages help_glossary_blocks, help_glossary_groupings, help_glossary_operations), help_costs, help_privacy, help_backup, help_translations, plus the three table-style pages help_home_icons, help_home_info_providers, help_home_ai_providers. Only those three help_home_* topics exist. The same map also carries four screen/topic pages that aren't home-page cards: about (the About screen), dependencies (third-party licences), and manual / technical_documentation (the two bundled-doc WebView screens — see below). That's why the map has 18 entries, not 14.

Live icon-legend overlay

On every screen that renders through the generic BottomIconBar and shows at least one bar icon, the white ❔ opens a full-screen live overlay titled "<screen title> - icons" (IconLegendOverlay). This used to be gated to an allowlist; it no longer is.

  • Lists the icons currently visible in that screen's bottom bar — two columns: the glyph, then the icon's name + a one-line description.
  • Tapping a row performs exactly what tapping that bar icon does — the overlay closes, then re-fires the icon's own action.
  • Per-icon name + description come from SCREEN_ICON_HELP[topic] in IconHelp.kt, with a generic fallback map DEFAULT_BAR_ICON_HELP (keyed by glyph) for any bar icon the screen's own legend doesn't cover.
  • The overlay's own single glyph is a red ❓ that opens the screen's main help page — the live overlay already covers the icons, so it doesn't also point at the static icon-table page.

LEGEND_OVERLAY_TOPICS (SharedComponents.kt, 57 entries — verified against source) no longer decides whether the bottom-bar ❔ shows — that's unconditional now. Its remaining job is on the HelpScreen side: for topics in this set, the main help page deliberately does not render the inline icon-table, nor the "❔ Icons on this screen" cross-link — the live overlay already replaced that content in the user flow. It covers the whole report-Manage family (reports_hub, report_run and its edit / create / get-info / icons / titles sub-editors), the Meta / secondary / fan-out / fan-meta drill-ins, the translation, tournament and judge-the-judges drill-ins, the Find-alternative and icon-lookup screens, the per-agent result / content / cost screens, regenerate_batch, report_notes, report_agent_chat.

Static icon-table page

The bottom-bar ❔ no longer links to a static page anywhere — that path was dropped when the live overlay was rolled out to every BottomIconBar screen. The static <topic>_icons help page still exists as content: a flat icon table (IconHelpTable, from SCREEN_ICON_HELP), reached only via the "❔ Icons on this screen" cross-link at the top of a topic's own main help page (itself opened by the red ❓).

ICON_HELP_AS_PAGE (IconHelp.kt, 20 entries — verified against source; originally curated as "whose screen shows more than 3 icons") selects which topics get a standalone page:

ICON_HELP_AS_PAGE — 20 topics
  • report_run, agent_edit, flock_edit, swarm_edit, provider_edit
  • report_single_result, secondary_detail, prompt_view, secondary_list
  • secondary_fan_out_l1/l2/l3
  • translation_run_l1, translation_run_l3
  • icon_lookup_main/agent/meta/translation/language/pair (6 topics)

Topics with 1–3 icons that aren't in this set embed the same table inline under their main help page instead of getting a standalone page (e.g. report_new — 3 icons — is deliberately kept out).

Both the cross-link and the inline table are suppressed for topics in LEGEND_OVERLAY_TOPICS — that screen's live overlay already covers the icons. Cross-referencing the two sets: 15 of the 20 ICON_HELP_AS_PAGE topics also sit in LEGEND_OVERLAY_TOPICS, so their standalone page is registered but effectively unreachable from the current UI. That leaves five ICON_HELP_AS_PAGE topics outside LEGEND_OVERLAY_TOPICS — agent_edit, flock_edit, swarm_edit, prompt_view, provider_edit — where the standalone <topic>_icons page is still reachable today, alongside (not instead of) the live overlay on their own bottom bar.

Topic shape

A help topic on the screen is a series of HelpCard rows:

HelpCard("Overview", "What this screen does, in one paragraph.")
HelpCard("Add card", "How to use the Add button, where it lands…")
HelpCard("Tips", "Small surprises worth knowing.")
HelpCard("Pitfalls", "Common mistakes / edge cases to avoid.")

Each card is a (title, body) pair; the body is plain text or markdown-flavoured. The auto-built <topic>_icons pages are the exception — they carry an empty cards list, since their table is rendered directly by HelpScreen from SCREEN_ICON_HELP.

The old "Related" card pattern was dropped. Cross-linking now happens two ways: deep-linking from the rest of the UI, and the RELATED_HOME_HELP table (HelpContent.kt), which renders a "Relevant Help pages" footer (RelevantHelpPagesCard) at the bottom of a per-topic page. Topics with no entry there render no footer.

Routing & the Help home page

  • helpForTopic(topicId) (NavRoutes.kt) builds "help/${encode(topicId)}" — URL-encoded so the id can carry colons / slashes / spaces. NavRoutes.HELP = "help".
  • Every screen's TitleBar takes a helpTopic: String and publishes it into the bottom-bar state; the single BottomIconBar at AppNavHost scope paints the strip + glyph(s). In Home-bar mode, HomeIconBar reads the same state and paints red help + trace in the persistent top strip instead.
  • The Help home page (/help, rendered by CompactOverview) shows: a Welcome card that interpolates AppService.entries.size for the provider count, a "Per-screen help" card, then 11 tap-through reference cards in order — About → Getting started → How it works (concepts) → Concepts & glossary → Costs → Privacy → Backup → Translations → Icons → Info providers → AI providers — a Copyright card, and a case-insensitive substring search box.
  • Search (searchHelp) scores every topic title (weight 3), card title (weight 2), card body (weight 1), collapses to the best card per topic, sorts descending, takes the top 12. A non-blank query suppresses all other home content. Per-topic pages have no own search — go back to Help home.
  • The per-topic page chrome (HelpFooter) renders a "More information" card: a Help-home row (per-topic pages only), an About row, and a GitHub: herbert256/ai row. Copyright is GPL v2.0, Herbert Groot Jebbink.

Per-provider & per-repository pages

Per-provider help

provider_edit plus one provider_* page per major cloud provider (34 verified against ProviderCatalogHelp.kt) — setup, capabilities, quirks, known issues. User-added / less-common providers fall through to the Help home page instead of a bespoke topic.

Reachable from every ℹ icon next to a provider name. The page id is providerHelpTopicId(serviceId) = "provider_" + lowercased, alphanumeric-only id. Per-provider pages share an infrastructure helper so each card has a uniform layout (providerCatalogHelp + CLOUD_PROVIDER_TAGLINES).

Per-repository help

12 info_provider_* pages, one per external metadata source (HuggingFace / OpenRouter / LiteLLM / models.dev / Helicone / llm-prices.com / Artificial Analysis / Requesty / llm-stats / genai-prices / TrueFoundry / CloudPrice) with endpoint, auth, what it provides, when fetched, where cached. Reachable from every Source button on Model Info and from the Trace detail ℹ.

The Trace detail screen's ℹ resolves the trace's URL + category to one of the 12 topics via the free function infoProviderForTrace(url, category) (HelpScreen.kt) — not a HelpResolver class (there is none). It calls infoProviderForUrl (host match, disambiguating shared hosts like raw.githubusercontent.com via urlPathPrefix) then, for dual-purpose services, gates on category so a plain chat completion doesn't hijack the ℹ. Only OpenRouter sets requiresChatCategoryGate = true; its gate set is INFO_FETCH_CATEGORIES = setOf("OpenRouter model specs"), plus any category starting with "pricing/".

Authoring guidance

Checklist for changing help topics
  • Reuse common card patterns (Overview / Add / Tips / Pitfalls) so users learn the structure once. Don't bring back "Related" cards inside a topic — wire RELATED_HOME_HELP instead.
  • Match topic IDs to the screen's helpTopic and the HELP_TOPICS map; an unmatched id renders an empty page.
  • When adding or changing a screen's bottom-bar icons, update its SCREEN_ICON_HELP[topic] rows in IconHelp.kt (glyph, short name, screen-specific description) — trace the actual TitleBar handler, never guess. Every screen with ≥1 bar icon gets the live overlay automatically now; once a screen's legend is complete, add its helpTopic to LEGEND_OVERLAY_TOPICS so the topic's own help page stops duplicating the table (for >3 icons, also add it to ICON_HELP_AS_PAGE for a standalone page instead of an inline one).
  • New screens should get a help topic. Exception: the Answer matrix view (ui/report/view/AnswerMatrix.kt) deliberately reuses the existing view_ai_report topic rather than adding its own.
  • When adding a new visual setting or default icon, update both the Settings topic and the focused UI-customization reference doc (kept outside this hub).

Bundled documentation (this hub)

Separately from the HelpContent catalog, DocumentationScreen (ui/admin/DocumentationScreen.kt) is a single WebView wrapper serving one of two bundled HTML doc hubs, chosen by a docsSubdir param:

Manual
assets/docs/manual/index.html
Route NavRoutes.DOCUMENTATION_MANUAL, title "Manual", helpTopic = "manual".
Technical
assets/docs/technical/index.html — this hub
Route NavRoutes.DOCUMENTATION, title "Technical documentation", helpTopic = "technical_documentation".

Both routes are defined in DeveloperRoutes.kt and reached from AboutScreen. Both helpTopic ids also exist as real HelpContent topics in GlossaryHelp.kt, so the WebView's own ❓ has a page to open. JavaScript is disabled (javaScriptEnabled = false); allowFileAccess = true, allowContentAccess = false. System back walks the WebView's own history (webView.canGoBack()) before popping the screen, giving a normal browser back experience across cross-doc links.
