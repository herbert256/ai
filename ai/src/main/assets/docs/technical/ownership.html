Runtime state ownership map

The single-writer reference for the app's mutable runtime state — who is allowed to write it, and where everyone else reads it from. Several central classes coordinate many domains at once (AppViewModel, ReportViewModel), and a refactor that moves state without knowing its owner is how mirrors and double-writes creep in.

The rule this page encodes: exactly one writer per entry. Everyone else either reads the owner's StateFlow or calls a method on the owner. A "mirror" (a second copy kept in sync by hand) is a smell — the only sanctioned mirror is SettingsHolder.

Process-scoped state (AppViewModel)

These flows live above any single Compose tree so they survive Activity config changes and screen navigation. All owned by AppViewModel.

UiState
writer AppViewModel · _uiState
General + AI settings, refresh ticks. Read by every screen via uiState.
Broken-work badge list
writer AppViewModel.setBrokenBatches · _brokenBatches
Top-bar badge, Broken-work screen. Re-published whole each 30 s scan tick — SecondaryRunManager.startBackgroundBrokenScan computes it, AppViewModel publishes it.
Pending "continue this batch" hand-off
writer AppViewModel.requestBatchOpen / consumeBatchOpen · _pendingBatchOpen
Manage screen's one-shot consumer.
Batch build-stage progress
writer beginBuild/updateBuild/finishBuild/clearBuild · _batchBuildProgress
Drives BuildStageOverlay. Engines write through the four methods via the shared BatchBuildScope helper — never touch the flow directly.
Throttled / running fan-out + fan-meta pair ids
writer AppViewModel.update*Pairs · _throttledFanOutPairs, _runningFanMetaPairs
L1 stats panels. These are throttle-gate-only overlays; the authoritative per-pair PairStatus is the FanOutEngine flow itself.
Refresh-all in-flight state
writer AppViewModel · _refreshAllState
Refresh-all screen; survives navigating away and back (re-attachable).
App-wide restart lock
writer AppViewModel.engageRestartLock · _restartLockActive
AppNavHost — greys the bars, swallows back presses.
Background broken-scan job handle
writer AppViewModel · backgroundResumeSweepJob
Only read by the scan's own cancel-prior guard.

Report-generation runtime (ReportViewModel)

ReportViewModel is a plain wrapper over AppViewModel, not an androidx ViewModel in its own right. Primary generation already has a formal ownership shape here:

Primary generation job + report id
reportGenerationJob, activeGenerationReportId
The job carries no id of its own; activeGenerationReportId is what the broken-work scan reads to tell a live PENDING/RUNNING agent from a process-kill-stranded one.
Single/all-agent regenerate jobs
regenerateJobs (keyed by report id)
deleteReport cancels by key so a terminal write can't recreate a deleted report's directory.
Is-this-report-live predicate
isReportGenerating(reportId)
Folds activeGenerationReportId + regenerateJobs + the regenerate-batch engine — the one place to ask.
Variation replay tracks
per-mode ReplayTrack (temperature / reasoning-effort / web-search / prompt-edit)
Each track owns its own StateFlow<Map<String,S>> plus its own job map.
Alt-icon fan-out jobs
iconFanOutJobs, languageIconFanOutJobs, agentIconFanOutJobs
Report / language / per-agent variants. Cancel-prior on re-launch; deleteReport prefix-cancels.
Per-agent streamed results
_agentResults
Kept as a separate flow from UiState so a single task's completion doesn't force a recompare of every other field.
Fan-out / tournament / judges runtime
fanOutEngine, tournamentEngine, judgeEvalEngine
Each engine is the sole owner of its own run state; the UI subscribes to the engine directly, not through ReportViewModel.

The in-flight fan-meta batch job is not a ReportViewModel field — it lives in the FanOutEngine run-job registry under a namespaced |meta| key, because it's a decorator pass over that engine's pairs, not a state of its own.

Secondary, metadata & cost state

Secondary results
owner SecondaryResultStorage
META / RERANK / MODERATION / TRANSLATE / fan-out rows / judged kinds — durable JSON. Lineage fields (fanInOf, fanOutSourceAgentId, metaPromptId, targetLanguage, tournamentRole, tournamentJudgeRunId) live on the row itself, not a side index.
Report metadata
owner ReportStorage via per-kind update methods
Icon / title / language / per-model title-icon. Generation is orchestrated by IconGenerationManager, but the writes still go through ReportStorage.
Global report-data invalidation tick
owner ReportDataVersion
One global StateFlow bumped by every report mutation; UI refresh ticks observe it instead of each screen tracking its own dirty flag.
Cost ledger per report
owner ReportStorage.reconcileApiCallCostLedger + usage reconciliation
Currently spans both ReportStorage and SettingsPreferences — a known consolidation target, not yet a single owner.

Persistence-layer settings & usage

General + AI settings, model lists, prefs keys
owner SettingsPreferences
The persistence facade every settings read/write goes through.
Saved prompt history
owner PromptHistoryStore
Already extracted out of SettingsPreferences; owns its own lock and cache.
Usage stats
owner SettingsPreferences static caches (today)
Token/cost counters with a debounced flush. A future extraction would move this into a dedicated usage-stats recorder and move the shutdown flush off AppViewModel.onCleared, but as of now SettingsPreferences is still the writer.

UI-derived state (Compose-local)

rememberReportRuntimeState (ui/report/manage/RuntimeState.kt) recomputes a large bundle of report/manage derived state — secondary counts/rows, translation + fan-out summaries, totals, icon/title/language fields, loaded-report fields — inside composition via remember + LaunchedEffect(currentReportId, iconRefreshTick).

It derives from the storage owners above; it is not itself an authority. Don't treat its output as a source of truth to write back to — recompute it from the real owner instead.

SettingsHolder — the one mirror

SettingsHolder.current (model/SettingsHolder.kt) is a deliberate static mirror of the latest aiSettings, written from a uiState.collect in AppViewModel — plus two eager direct writes inside setDisabledInfoProviders so the info-provider toggle is visible to PricingCache's gated finders before the off-main recompute finishes. AppViewModel is still the sole writer.

It exists so dispatcher helpers that can't thread a Settings reference through their call stack (e.g. ApiDispatchBuilders.isReasoningCapableForDispatch, now a thin delegate to ModelCapabilityResolver) can still answer capability questions.

This is the only sanctioned mirror in the app. New code should prefer an explicit context/resolver parameter and treat the holder as the fallback path, not the primary one.

How to use this map

  • Adding runtime state? Pick one owner from this list (or add a new entry). Don't keep a second copy elsewhere "for convenience".
  • Refactoring an owner? Keep this map in sync in the same change.
  • Tempted to mirror a flow into another layer? That's the signal to expose the owner's StateFlow to the reader instead of copying it.
