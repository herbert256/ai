Get info & Regenerate report

Two related Manage-hub surfaces. Get info is a status board for a report's metadata jobs (icon, language, title, per-model icon / title). Regenerate report is the orchestration engine that re-runs everything on a report — metadata + agents + every secondary result — in a fixed phase order, surviving app restarts and pausing on the first error.

Get info

The Manage hub collapses the separate metadata-generation jobs into one info row (InfoSummaryRow, ui/report/manage/SummaryRows.kt:80). It is always the first row on Manage — the three summary rows render info → regenerate → second. Tapping it opens ReportGetInfoScreen (ui/report/manage/GetInfo.kt:360), help topic report_get_info. It's a layer over Manage (publishBottomBar = false) — Manage keeps publishing its own bottom bar underneath.

Title-tap cycle (cycleReportScreens, ui/report/manage/Run.kt:164): tapping the title bar cycles Manage → Get-info → second-results → Manage, unconditionally — the second-results step used to be skipped when the report had no secondary results, but is now always one tap away. Back / the report icon still peel one layer back to Manage instead of advancing. The second results screen is Get-info's secondary-result analogue (rerank / meta / moderation / translate / fan-out / tournament / judges / compare / rank collapsed into one board) — see secondary-results.

buildInfoJobs (ui/report/manage/GetInfo.kt:89) is the single source of truth for the rows, shared by the Info screen and the Manage info row so the two never disagree. Only enabled jobs are emitted (per the relevant setting gate), split into five report-level jobs plus two per-model jobs, in run order:

Terminal guards

Several guards exist so a stalled or never-run job doesn't spin the Manage hourglass forever:

*NeverRan
A finished report (completedAt != null) that recorded no attempt at all — no icon/title/language, no error, no cost / duration / promptUsed — reads as "never ran" rather than Queued… forever. Covers legacy reports and copies/fan-out-derived reports whose metadata was inherited.
modelIconAttempted / modelTitleAttempted
GetInfo.kt:64, :72
Per-model analogue: a call that concludes with markers recorded (cost / tokens / duration / prompt-name) but no result and no error (e.g. an empty/unparseable reply) settles model-title to EMPTY ("· no title") and model-icon to DONE instead of spinning.
Phantom-RUNNING guard
GetInfo.kt:268, :312
A finished report whose per-model job left no markers at all (imported/copied report, or per-model icon/title toggled on after generation) used to fall through to else -> RUNNING and spin forever. titleStateFor / the icon-state when now short-circuit on completedAt != null to terminal (EMPTY for title, DONE for icon) before that fallback. During live generation completedAt is null, so a freshly-succeeded model still correctly shows RUNNING while its enrichment call is in flight.
reportPending
GetInfo.kt:110
Report-level analogue: a report-level CLOCK keeps the aggregate spinning only while completedAt == null; once the report is finished an unstarted job reads as terminal (still shown as ⏳) and doesn't pin the Manage row to ⌛.

aggregateInfoState (GetInfo.kt:329) drives the Manage row's status cell: ❌ if any job FAILED, else ⌛ while any job is still genuinely pending, else ✅ (or the report's own icon). A CLOCK left by an ERRORed or STOPPED model is not pending (perModelPending, GetInfo.kt:277) — a finished report with one failed model settles to ✅ rather than spinning forever.

Info regenerate entry points

Both are scoped to info jobs only — model responses + secondary results are left untouched, and each new call's cost is added on top of the report's existing spend:

Bottom-bar 🔄 (Manage reload)
regenerateReportInfo · ReportViewModel.kt:2024
Re-runs language, title→icon, and per-model enrichment for every successful agent. Confirm dialog forks on whether the Get-info layer is up (Run.kt:740); pops "Regenerate report info?" first.
"Restart errors" button
restartReportInfoErrors · ReportViewModel.kt:1981 · shown only when ≥1 job is FAILED (GetInfo.kt:501)
Clears the error state of only the errored rows and re-fires just the failed side (title-error re-runs title→icon together since the icon derives from the title; per-model re-runs only the side — icon or model-title — that errored).

⚠️ lights immediately on error. The Manage hub stays composed underneath the Get-info / second-results layers, so its reportHasError check (Main.kt:410 — any FAILED info job, any FAILED secondary, or any errored agent) fires a LaunchedEffect that forces a Broken-work scan immediately (LocalRefreshBrokenWork), surfacing the top-bar ⚠️ badge the instant a red ❌ appears on Manage / Get-info / second-results, instead of waiting out the 30-second background sweep.

Regenerate batch engine

RegenerateBatchEngine (viewmodel/RegenerateBatchEngine.kt:53, a class with an internal constructor taking (appViewModel, reportViewModel)) is the authoritative runtime owner of the per-report "Regenerate report" job. It replaces the legacy one-shot regenerateReport with a phased, app-restart-survivable orchestrator.

  • State lives on disk via RegenerateBatchStorage (one JSON per report); an in-memory StateFlow<Map<reportId, RegenerateJob>> (_jobs) mirrors it for live UI.
  • The orchestrator is one coroutine per report, scoped to AppViewModel.viewModelScope (survives navigating away from Manage) and tracked in orchestratorJobs (ConcurrentHashMap<String, Job>) so a cancel can .cancel() it.
  • Public API: hasJob, hydrate, enqueueAndStart, restart, cancel, cancelJobNow, reconcile, detectBroken, isActivelyRunning, deleteJob.

Phase order

RegeneratePhase (data/RegenerateBatch.kt:20) is a 10-value enum in fixed order; the orchestrator walks forward by ordinal. enqueueAndStart starts at RegeneratePhase.values().firstOrNull() — not a hardcoded phase — so prepending a phase can't silently skip it.

TITLEphase 1

Re-runs report title workers — short + long (synthetic row __report_title__) — runs before ICON so the icon can derive from the fresh long title.

Dispatcher: iconGen.kickOffReportTitleGeneration(…, thenIcon = false) · row status from Report.titlePromptUsed / titleErrorMessage

ICONphase 2

Re-runs the report's 🎯 icon (synthetic row __report_icon__).

Dispatcher: iconGen.kickOffIconGeneration · row status from Report.icon / iconErrorMessage

LANGUAGEphase 3

Re-runs language detection + language-icon (synthetic row __report_language__).

Dispatcher: iconGen.kickOffLanguageGeneration · row status from Report.languageName / languageIcon / languageIconErrorMessage

AGENTSphase 4

One task per ReportAgent whose provider still resolves.

Dispatcher: forceRegenerateAllAgents · row status from ReportAgent.reportStatus + responseBody

METAphase 5

Single-call meta rows (fanOutSourceAgentId == null && fanInOf == null) plus RERANK and MODERATION. JUDGES / COMPARE are excluded.

Dispatcher: secondary.resumeStaleMetaPlaceholder (per row) · row status from SecondaryResult.content / errorMessage

FAN_OUTphase 6

Fan-out per-pair rows (fanOutSourceAgentId != null).

Dispatcher: fanOutEngine.resumeStaleRunsForReport(…, resetAttempts = true) · row status from SecondaryResult.content / errorMessage

FAN_INphase 7

Fan-in combined rows (fanInOf != null).

Dispatcher: secondary.resumeStaleMetaPlaceholder (per row) · row status from SecondaryResult.content / errorMessage

TRANSLATIONSphase 8

Every TRANSLATE row.

Dispatcher: translation.startMissingTranslations (per distinct translationRunId) · row status from SecondaryResult.content / errorMessage

FAN_METAphase 9

Per-fan-out-pair title + icon — one worker call produces both — for pairs that previously carried a title/icon (or an error).

Dispatcher: iconGen.runFanMetaBatch (per metaPromptId) · row status: icon present → Success; iconErrorMessage/titleErrorMessage with no icon → Error

TOURNAMENTphase 10

Tournament per-match rows (kind == TOURNAMENT && tournamentRole == "MATCH"). The AGGREGATE ranking row is not a task — it makes no API call; the tournament engine recomputes it once the match rows settle.

Dispatcher: tournamentEngine.resumeStaleRunsForReport(…, resetAttempts = true) · row status from SecondaryResult.content / errorMessage

The old separate per-icon-tier phases are gone — FAN_META is one phase because the workers/fan-meta prompt returns a title: / icon: reply in one call. JUDGES and COMPARE are owned by their own engines (JudgeEvalEngine / CompareEngine) and deliberately excluded from the regenerate batch (isMetaPhaseRow, RegenerateBatchEngine.kt:957, which excludes TRANSLATE, TOURNAMENT, JUDGES, COMPARE plus fan-out / fan-in rows).

TRANSRANK falls through to META. "Rank the translators" (the 8th SecondaryKind) has no dedicated regenerate phase and is not excluded by isMetaPhaseRow. Its rows carry tournamentRole (TRANSRANK_ROLE_CELL / _AGGREGATE) and a translationRunId but no fanOutSourceAgentId / fanInOf, so a TRANSRANK row lands in the generic META phase and is resumed via the single-call resumeStaleMetaPlaceholder path rather than re-judged by TranslatorRankEngine. Translator-rank batches are best resumed from their own "Rank the translators" screen instead — see secondary-results.

FAN_OUT and TOURNAMENT pass resetAttempts = true so a user-initiated regenerate clears any per-session retry counts a prior manual resume ran up — otherwise the pair/match would terminalize instantly and never re-fire.

buildTaskList (RegenerateBatchEngine.kt:793) builds the task set from the report's current contents:

  • TITLE / ICON / LANGUAGE only fire when the matching setting gate is on, the report has a non-blank prompt, and the matching worker prompt has a resolvable worker — so the engine doesn't park on a synthetic row that could never be dispatched.
  • AGENTS skips any agent whose provider no longer resolves (AppService.findById(agent.provider) == null), matching the same drop in forceRegenerateAllAgents — otherwise its row would reset to PENDING but never re-fire and hang the phase to the 30-minute timeout.
  • FAN_META only targets pairs that previously carried an icon / title (or an error), so the engine doesn't spin on rows that can never land.

Phase step machine

Per phase, orchestrate (RegenerateBatchEngine.kt:286) loops:

  1. Empty phase → advanceToNextPhase, continue.
  2. Flip every task in the phase to RUNNING (not just WAITING — on a restart the prior ERROR task and its already-SUCCESS siblings must be re-armed too, or awaitPhaseCompletion — which only transitions RUNNING tasks — would leave them stuck), set startedAt, clear endedAt / errorMessage; then resetRowsForPhase resets the underlying rows on disk (Manage shows ⌛). All reset helpers are the *KeepingCost variants (clearReportTitleKeepingCost, clearReportIconKeepingCost, resetAgentToPendingKeepingCost, clearFanOutTitle/IconStateKeepingCost, …) — prior spend stays and the dispatcher's additive cost write adds the new call's cost on top.
  3. dispatchPhase fires the phase's dispatcher (see table above).
  4. awaitPhaseCompletion (RegenerateBatchEngine.kt:350) polls disk every 1500 ms, flipping each RUNNING task to SUCCESS / ERROR / CANCELLED from the row's on-disk content / errorMessage. A 30-minute per-phase timeout is a safety net (pauses the phase on timeout).
  5. Halt on the first ERROR row → pauseOnError; otherwise once every task is terminal, advanceToNextPhase.

readRowStatuses (RegenerateBatchEngine.kt:422) dispatches the status read per phase; the synthetic TITLE / ICON / LANGUAGE rows read Report fields directly (no persistent row to match), and the FAN_META read treats an icon present as a usable (partial) success.

Job & task states

RegenerateJobStatus.RUNNING
Orchestrator coroutine is alive and stepping through phases.
PAUSED_ON_ERROR
At least one task ended ERROR; no further phases fire until restart succeeds.
DONE
Every task ended SUCCESS / CANCELLED.
CANCELLED
User clicked Cancel; Restart re-enters at currentPhase.
RegenerateTaskState.WAITING
Task hasn't been touched yet — its phase still pending.
RUNNING
Phase started, dispatcher fired, awaiting the underlying row's success/failure.
SUCCESS
The underlying row now has content (or an icon for FAN_META) and no errorMessage.
ERROR
The underlying row carries an errorMessage / iconErrorMessage after the dispatch fired.
CANCELLED
Phase didn't get to fire because the user clicked Cancel.

Pause-on-error & background resume

On the first ERROR in a phase the job persists status = PAUSED_ON_ERROR and stamps pausedOnRowId (the first errored row). No further phases fire until a restart succeeds. All resume paths are idempotent:

restart
RegenerateBatchEngine.kt:124
The Restart button on the detail screen — the only user-facing resume trigger. For a paused job it only resumes when the paused row is no longer errored on disk (isRowStillErrored); otherwise no-op. A CANCELLED job always restarts at currentPhase. DONE and an already-live RUNNING orchestrator are no-ops.
reconcile
RegenerateBatchEngine.kt:192
Retained for the manual resumeStaleRunsForReport orchestrator — explicit/manual-use only now (fired by user Regenerate / retry, not on report open). DONE / CANCELLED → no-op; RUNNING with a dead orchestrator (app kill) → revive; RUNNING with a live orchestrator → no-op; PAUSED_ON_ERROR with the row now OK → resume; still errored → no-op. No longer called from the background pass — the 30 s startBackgroundBrokenScan is now detect-only; a RUNNING-but-dead / PAUSED_ON_ERROR job surfaces on the ⚠️ Broken-work screen instead of being auto-revived.
detectBroken
RegenerateBatchEngine.kt:236
Read-only counterpart to reconcile used by that scan: true when the job is PAUSED_ON_ERROR, or RUNNING with no live orchestrator in this process (app-kill-interrupted); false for DONE / CANCELLED and a genuinely-live orchestrator. detectBrokenBatchesForReport (SecondaryRunManager.kt:754) turns a true into one synthetic BrokenBatch(kind = REGENERATE) — "Paused on an error" when PAUSED, "Interrupted mid-run" when RUNNING-but-dead.
isActivelyRunning
RegenerateBatchEngine.kt:251
True while a live orchestrator coroutine exists in this process; the Broken-work agent scan reads it so a mid-batch report's PENDING/RUNNING agents aren't mistaken for app-kill-stranded ones.
cancel
RegenerateBatchEngine.kt:167
Stops the orchestrator; in-flight HTTP calls finish themselves and persist. Only the orchestrator's own finally decrements activeSecondaryBatches — cancelling used to decrement it too, drifting the badge below the real count.
cancelJobNow
RegenerateBatchEngine.kt:160
The synchronous variant used by deleteReport, which must stop the orchestrator before removing the report dir (the async cancel returns before its launch body runs).

mutateJob does an atomic get → mutate → save under RegenerateBatchStorage.update's single lock, so a concurrent cancel can't be clobbered by an orchestrator update built from a stale RUNNING snapshot. activeSecondaryBatches on UiState is incremented while an orchestrator is alive (startOrchestrator) and decremented in finally, so the app-wide "work in flight" indicator counts regenerate batches too.

UI

RegenerateBatchScreen (ui/report/manage/RegenerateBatch.kt:70), help topic regenerate_batch, title "Regenerate report" / subject "Re-run every model on this report" — a status banner (phase / counts / "paused on error"), an action row (Cancel when RUNNING, Restart when PAUSED / CANCELLED), and per-task cards grouped by phase (phase chip via the RegeneratePhase.label map, timestamps, duration, error). It's mounted as a RegenerateBatchOverlay wrapping the screen in LocalNavigateToCurrentReport. The bottom-bar 🗑 pops a confirm dialog, then routes through deleteJob (cancels the orchestrator, drops the JSON + memory entry).

RegenerateBatchManageRow (ui/report/manage/RegenerateBatch.kt:370) renders the top-of-list regenerate row on Manage, keyed to the current report only (via LocalCurrentReportIdForSwipe) so a leftover job from another report can't surface on an unrelated one. Its label is "<done> / <total> · <currentPhase.label / status>".

Find alternative title / icon

Both are transient fan-outs launched from a metadata detail screen (model picker → N picks), separate from the regenerate batch and from Get-info's own regenerate buttons. "Find alternative icons" is documented in report-icons. "Find alternative titles" lives in IconGenerationManager.kt (startReportTitleFanOut / startModelTitleFanOut / startPairTitleFanOut / runTitleCandidate):

  • Resolves the alt/report_title[_long] (report) or alt/model_title (per-model and per-fan-out-pair) internal prompt; dedupes picks by provider:model; pre-populates TitleCandidate.Running rows in titleFanOutByReport / titleFanOutByAgent / pairTitleFanOutByPair (in-memory).
  • Each pick pre-acquires the per-provider ProviderThrottle permit (sets permitPreAcquired so the interceptor doesn't double-count) and runs analyzeWithAgent on a synthetic Agent, traced under the alt/report_title[_long] / alt/model_title category.
  • Cost-recorded even though the picked title only fills the editor field: when the call returns any tokens it posts to the global Usage ledger via updateUsageStatsAsync(kind = "title") and appends an IconCallRecord (with tier = 0, blank agentId so agent/pair icon-clearing never sweeps it, and type = the trace category) via ReportStorage.appendIconCall, so the spend shows in the report cost table + totals. See costs.
