AI Workers — Agents, Flocks, Swarms

Three saved "worker" types bundle model picks (plus their parameter / prompt resolution) for one-tap reuse. They play two roles: one-tap model selection when starting a report or chat, and the pool that every single-call internal kind (rerank, moderation, meta, fan-in, translate, icon+title, transrank, tournament) dispatches through.

The three kinds

They nest — a Flock groups Agents, a Swarm groups bare provider/model pairs. All three live on Settings (agents, flocks, swarms) and round-trip through Import/Export. The three glyphs are the factory MetadataDefaults constants — AGENT = 🤖, SWARM = 🐝, FLOCK = 🫒 (data/MetadataDefaults.kt) — and are user-overridable via the metadata-icons editor.

Agent 🤖
one named config
A single (provider, model) pair plus optional Parameters presets, an optional system prompt, and an optional per-agent API key / endpoint override.
Flock 🫒
a named group of Agents
Holds member agent ids plus its own Parameters presets and system prompt.
Swarm 🐝
a named group of (provider, model) pairs
Holds bare member pairs plus its own Parameters presets and system prompt — no agent id, no key override.

Field notes — resolution, live references, reserved flock
  • Agent apiKey / model are overrides, not requirements. Both fall back to the provider's stored value through resolver helpers: 
    fun getEffectiveApiKeyForAgent(agent) = agent.apiKey.ifBlank { getApiKey(agent.provider) }
fun getEffectiveModelForAgent(agent)  = agent.model.ifBlank  { getModel(agent.provider) }
    getModel(service) returns service.defaultModel and getApiKey(service) returns the stored provider key — so an agent left on a provider's default-model alias resolves at use time, not at save time.
  • Flock stores agent ids, not copies — getAgentsForFlock maps them back live, so editing an agent updates every flock that references it. Ids that no longer resolve are silently skipped (mapNotNull).
  • Swarm members are bare pairs — no agent id, no key override; they carry only the swarm's own paramsIds.
  • A reserved flock named default agents (DEFAULT_AGENTS_FLOCK_NAME) is auto-managed: the per-provider Test button (via markProviderTestedOk → Settings.ensureDefaultAgentInFlock) adds the provider's tested model as an agent and joins it to this flock; the Refresh All → Providers / models / default agents step (and the standalone Refresh workers step) empties it first, then repopulates it from each provider's worker phase (runWorkerPhase).

Bundled seeds

Swarms and flocks ship pre-seeded from assets/. Each bundled item is its own JSON file — no single workers/swarms.json / workers/flocks.json any more:

assets/workers/swarms/<name>.json
SwarmSeed.kt, DIR = "workers/swarms"
One file per swarm — a whole Swarm ({ id, name, members:[{provider,model}], paramsIds }); the filename is cosmetic, the in-file name is authoritative. Member provider strings resolve to AppService through the same createAppGson adapter Import/Export uses.
assets/workers/flocks/<name>.json
FlockSeed.kt, DIR = "workers/flocks"
One file per flock. Members are stored by agent name (agentNames, with a legacy agentIds fallback) so the bundle is portable; they're re-linked to install-local agent ids against the current agent set at load — exactly like the Import/Export re-link path.

Merge is idempotent and non-destructive. On launch AppViewModel reads the assets and calls SwarmSeed.ensureAllPresent / FlockSeed.ensureAllPresent: any bundled item whose name (case-insensitive) is not already present is appended with a fresh UUID; existing rows — including user edits to a same-named swarm — are left strictly alone. A single unparseable / unknown-provider file is skipped, not fatal. Flocks seed after agents so their agentNames resolve.

The AI Workers setup hub

Settings → AI Setup → Workers opens WorkersSetupScreen (ui/settings/SetupScreens.kt), a sub-hub with three nav cards plus a model-search entry. The AI Setup landing's own Workers card (subtitle "Agents, Flocks, and Swarms", badge = agentCount + flocks.size + swarms.size) and all sub-cards are gated on hasApiKey (Settings.hasAnyApiKey()) — disabled until at least one provider has a key set. The Agents card badge counts only agents whose provider is active (state "ok"); the Flocks and Swarms badges show the raw flocks.size / swarms.size.

CRUD shape

Each worker CRUD is a small Mode state machine — List / Edit / Add (no separate read-only View step) — over the shared CrudListPage framework:

  • ui/cruds/workers/agents/ — list.kt / add.kt / edit.kt
  • ui/cruds/workers/flocks/
  • ui/cruds/workers/swarms/

Tapping a row jumps straight to Edit — the CrudListPage's onView handler is wired to Mode.Edit(it), so the read-only view is skipped and the 👷 copy + 🗑 delete icons live on the edit bar. onAdd opens Mode.Add.

The thin CRUD Edit/Add wrappers delegate to the rich legacy forms — AgentEditScreen, FlockEditScreen, SwarmEditScreen. The agent form additionally needs AgentEditDeps (model fetch, Test button, fetch-error map, endpoint persistence, trace-link callback).

Copy / Save / Delete semantics

Copy is the 👷 duplicate affordance inside the legacy edit form: it appends -copy to the name, and a Save in that state writes a fresh UUID, so the duplicate lands as a new item rather than overwriting the original; the duplicate name is treated as a collision against the source so the user can't save <name>-copy over it.

Save upserts by id (replace-if-id-present, else append). Delete is a confirm-dialog that calls removeAgent / filters the list.

The legacy view screens (AgentViewScreen / FlockViewScreen / SwarmViewScreen) — reachable from older entry points outside the new CRUD list — each render their prompt + params via the shared WorkerSharedCards (ui/settings/CommonViewWorkerCards.kt), identical for all three because they share the paramsIds + systemPromptId shape.

Help topics: crud_agents, crud_flocks, crud_swarms (ui/admin/CrudHelp.kt) and setup_workers (ui/admin/SettingsAdminHelp.kt).

How workers feed model selection

Workers are never "run" directly — they expand into ReportModel targets during the report/chat selection phase. SelectionOverlays (ui/report/start/SelectionOverlays.kt) wires the three pickers to expander functions in model/SettingsModels.kt:

Agent pick
expandAgentToModel
Yields one target, or null if the provider is inactive.
Flock pick
expandFlockToModels
One target per active member agent.
Swarm pick
expandSwarmToModels
One target per active member pair.

Inactive-provider members are silently dropped — every expander filters on isProviderActive. The resulting ReportModel carries a type/sourceType tag and the resolved key/params:

  • Agent → ReportModel(provider, effectiveModel, "agent", "agent", agent.name, agent.id, agentId = agent.id, endpointId, effectiveApiKey, agent.paramsIds).
  • Flock → one per member, same shape as the agent target but sourceType = "flock", sourceId = flock.id, and paramsIds = flock.paramsIds + agent.paramsIds — the flock prepends its own ids to each agent's.
  • Swarm → ReportModel(member.provider, member.model, "model", "swarm", swarm.name, swarm.id, paramsIds = swarm.paramsIds) — no agentId, no key override.

Pickers add into the active target bucket, then the whole list runs through deduplicateModels. Dedup keys by deduplicationKey = "${provider.id}:$model" into a LinkedHashMap (first-appearance order preserved); on a collision an agent-sourced entry (non-null agentId — a direct agent or a flock member) replaces a bare manual / swarm pick, so the surviving row keeps the api key and parameter ids.

The flock and swarm pickers (ui/other/Selection.kt) show a per-worker cost estimate (summed across active members), an active-vs-total member count, and an ℹ️ info screen listing each member with provider, model, capability badges, and cost. Chat reuses the agent picker directly: picking an agent navigates to aiChatWithAgent(id).

The worker swarm — single-call secondary dispatch

The second role. The "workers"-category InternalPrompts that drive the internal kinds — rerank, moderation, meta, fan-in, translate-text / translate-title / translate-rank, find-translation, report/model/translation icons + titles, tournament, user-note — each carry an ordered workers fallback chain. Every bundled worker prompt ships with a single chain entry — the workers swarm — so the cheap 12-member swarm is the default model pool for all of these single-call kinds. There's no tournament-specific pool; tournament.json also points at workers.

A Worker is one of four kinds, told apart by which field is non-*N/A: Model (provider+model), Agent (agent name), Flock (flock name), Swarm (swarm name). Settings.expandWorker flattens a Flock → one agent-name worker per active member agent, and a Swarm → one provider+model worker per active member, so each member becomes its own fallback candidate; resolveWorker turns a single worker into a dispatchable Agent (a pinned provider+model yields a synthetic agent; a named agent is looked up in agents).

Two engines consume the chain, both shuffling the expanded members so a single-call kind picks one at random and a batch spreads across the pool:

SecondaryRunManager.runSecondaryViaSwarm

viewmodel/SecondaryRunManager.kt. One single-result secondary row (rerank / moderation / meta / fan-in / translate / transrank). Expands the swarm, tries members in shuffled order, re-stamps the placeholder's provider/model to whoever is being tried (so success attributes the row to the model that answered), parks a 429/529 member on a short cooldown (WORKER_429_DEFAULT_MS) and falls through; the row stays ERROR only when the whole chain is spent.

WorkerRunner

viewmodel/WorkerRunner.kt. The no-UI internal-prompt engine (report/model/language icons + titles). Random per-call order, per-worker 429 cooldown (honouring Retry-After), an accept predicate that treats a 200 with no usable artifact as a logical miss, and a session-scoped disable for 404/410 ("model gone") members. A pass where every candidate is cooling waits for the earliest cooldown to lift and re-runs the chain (up to 3 extra passes, 20 s per-wait cap) before settling on AllRateLimited — so a 5 s 429 blip across the pool doesn't mass-error a batch. Under a throttled batch the wait runs permit-free: runThrottledBatch's dynamic-host path installs ProviderThrottle.poolCoolingWaiter, which releases the item's sub-cap + global permits for the sleep and re-acquires them before the next pass, so cooling items don't throttle the rest of the batch. See report-icons for the full engine.

Run-time worker source — a worker prompt's modelSelection is *CONFIGURED (default — run against the prompt's saved workers) or *SELECT (show the +Agent/+Flock/+Swarm/+Model picker just before the work starts and run against the user's pick; never written back).

Per-report worker config — "Report - setup"

The old single ♻️ models-as-workers flag is replaced by a per-report Report.workerConfig: ReportWorkerConfig (data/ReportModels.kt), picked on the "Report - setup" screen (composable ReportSelectWorkersScreen, ui/report/start/SelectWorkers.kt) — the step between "Report - select models" and "Manage a report" that also hosts the Generate report button — and editable later via the Manage bottom-bar 👷‍⚕️ icon (same screen, Save instead of Generate; ReportStorage.setWorkerConfig). "Report - setup" itself holds the System prompt, Parameters and Second result options cards plus a Workers nav card; tapping Workers opens a nested full-screen Workers step (ReportWorkersScreen, same file) that holds four worker-routing cards:

Report info
reportInfo: PROMPT | CUSTOM + reportInfoWorkers
Who generates the report icon, short/long titles, and language name + icon. CUSTOM swaps each prompt's chain for the per-report worker group (InternalPrompt.withReportInfoWorkers).
Model info
modelInfo: PROMPT | OWN_MODEL
Who generates each answer's per-model title + icon. OWN_MODEL runs them on the answer's own model (InternalPrompt.withOwnModelWorker → singleModelWorker).
Worker batches ("Batches" card)
batches: PROMPT | REPORT_MODELS | SELECT_EACH | SELECT_ONCE + batchWorkers, workerSelection: WHEN_AVAILABLE | ROUND_ROBIN
The pool for Fan Meta, Translation, Tournament, Compare. Rerank / Moderation are exempt — they pass alwaysPromptWorkers = true, so they always run on their own prompt's workers. Judge-the-judges / Rank-the-translators have no worker selection at all: each reuses the participants of the batch it evaluates — Judge-the-judges judges with the distinct judges recorded on the report's completed Tournament MATCH rows; Rank-the-translators ranks with the distinct translation models of the connected Translation run (translatorJudges). Both are type-A fixed-judge batches and their launches no longer open a worker picker.
Meta / Fan-in ("Meta" card)
metaBatches / metaBatchWorkers / metaWorkerSelection, same option set
Routes on its own mirror set so it can draw from a different pool than the other batches. Resolution passes meta = true to resolveBatchSwarm / workerPlanFor / workerScheduleFor / launchWithWorkerPlan for these two.

A "Use report models" switch at the top of the Workers step (useReportModels) is a one-tap shortcut that force-sets modelInfo = OWN_MODEL, batches = REPORT_MODELS + workerSelection = ROUND_ROBIN, and metaBatches = REPORT_MODELS + metaWorkerSelection = ROUND_ROBIN, hiding the Model info / Batches / Meta cards underneath it while it's on. The "Report - setup" screen's own Second result options card (secondResultSelectScope, secondResultRuntimeParams) is unrelated to worker routing — it gates whether launching a Meta / Fan-out secondary from the second-results hub first shows a scope picker / a runtime prompt editor, or runs straight with the defaults.

Batch-pool precedence lives in one place — resolveBatchSwarm / InternalPrompt.withBatchWorkers (viewmodel/ReportViewModelHelpers.kt): REPORT_MODELS (→ reportModelWorkers(report), the report's own answer models distinct by provider:model) > an explicit runtime pick > a persisted SELECT_ONCE group > the prompt's configured chain. The UI side of the same decision is workerPlanFor + launchWithWorkerPlan (ui/report/manage/RuntimeWorkerPicker.kt), used by all eleven type-B launch sites: PROMPT honours the prompt's *SELECT picker; SELECT_EACH forces the picker on every batch; SELECT_ONCE shows it once — the first pick is persisted first-write-wins via ReportStorage.setBatchWorkersIfEmpty and reused by every later batch (engine-internal launches — fan-meta auto-start, resume, regenerate — never show a picker and fall back to the configured chain until a group is stored); REPORT_MODELS never asks.

Worker selection (round robin) — under REPORT_MODELS the workerSelection sub-choice picks the scheduling: WHEN_AVAILABLE keeps the historical shuffled pick (fast models absorb more work); ROUND_ROBIN deals consecutive calls to consecutive pool members via a process-wide per-report cursor (WorkerRotation + WorkerSchedule, viewmodel/WorkerRunner.kt), so every worker gets ~the same share. A slow worker keeps its items (nothing reassigns on slowness); 429 / 404 / logical-miss fall-through advances an item to the next worker in rotation, so an erroring worker may end up with less. WorkerRunner.run and runSecondaryViaSwarm share the cursor; the engines thread the schedule through runPooledItemCall (viewmodel/SecondaryCellCalls.kt). Fixed-judge grids (Judges / TransRank cells) and the fan-meta per-pair single-model pool have no pool pick, so the mode is a no-op there.

Parameter + system-prompt resolution

Agents (and flocks/swarms) carry paramsIds + systemPromptId references. The full merge precedence — how multiple presets fold (mergeParameters), how the report-generation agent / swarm chains layer selection / report-level / app-wide overrides, and how an agent system prompt combines with a Parameters preset's own prompt — is documented once in the dedicated docs: parameters (presets + merge precedence) and system-prompts (system-prompt resolution). In brief: resolveAgentParameters(agent) = mergeParameters(agent.paramsIds) ?: AgentParameters(); mergeParameters folds presets left→right with "later non-null wins" for scalar/string fields, OR for responseFormatJson/searchEnabled/webSearchTool, and AND for returnCitations.
