# Report Section View

The report section is the app's largest and most complex functional
area. This file maps the report lifecycle and the report-specific
features that sit on top of it.

## Observation 1 - A Report Is a Durable Multi-Model Run

Functional view: one prompt is executed against many selected models.
Each answer becomes a `ReportAgent` row with status, content, metadata,
cost, usage, traces, title/icon fields, and error state.

Source view: `ReportViewModel`, `ReportStorage`, `Report`, `ReportAgent`,
`ui/report/manage/**`.

Design implication: the report is the durable unit, while rows are the
per-model execution units. Deleting or regenerating rows must preserve
report-level continuity.

## Observation 2 - Start Flow Resolves Multiple Selection Sources

Functional view: the Start flow can build a report from direct models,
agents, flocks, swarms, previous reports, examples, previous prompts,
parameters, system prompts, images, web-search flags, and reasoning
settings.

Source view: `ui/report/start/**`, `ui/other/SelectionScreen.kt`,
`SettingsModels.kt`, `parameters.md`, `system-prompts.md`.

Design implication: report creation is a resolver pipeline, not a
simple form submit. UI labels should make it clear which layer supplied
each behavior.

## Observation 3 - Generation State Is User-Visible

Functional view: the user sees per-agent progress, success/failure
status, total completion, stop/cancel controls, and cost accumulation
while generation is running.

Source view: `BuildProgress`, `ReportViewModel`, `ReportStorage`,
`ui/report/manage/RuntimeState.kt`, `ui/report/manage/Run.kt`.

Design implication: progress state is a product requirement. Background
generation, cancellation, and recovery all need visible transitions.

## Observation 4 - Metadata Generation Is a Secondary Background Track

Functional view: report icons, report language/icon, short/long titles,
per-model titles, and per-model icons are generated by worker prompts
around the primary report run.

Source view: `IconGenerationManager`, `workers/report-icon`,
`workers/model-titles`, `workers/model-icons`,
`report-icons.md`, `regenerate.md`.

Design implication: a report can be functionally complete while
metadata jobs continue, fail, or are disabled. UI should not make
metadata success a precondition for opening report content.

## Observation 5 - Manage Screen Is an Action Console

Functional view: Manage shows answer rows and the main action strip:
view, edit, create, chat, copy, share, regenerate, trace, delete, pin,
notes, rerank, moderation, translate, fan-out, tournament tools, and
worker reuse.

Source view: `ui/report/manage/**`, `ReportRoutes.kt`, `TitleBar`,
`BottomIconBar`, `MetadataIcons`.

Design implication: most report actions originate from one console.
Adding a new action needs decisions about bottom-bar placement,
single-shot reuse behavior, help text, and export visibility.

## Observation 6 - Title and Icon Gestures Are Functional Navigation

Functional view: tapping the title cycles Manage, Get-info, and second
results; tapping the report icon opens the View hub. These gestures are
part of normal navigation, not decorative shortcuts.

Source view: `ui/report/manage/Run.kt`, `ReportSecondResultsScreen`,
`ViewAiReportScreen`.

Design implication: discoverability relies on consistent title-bar and
icon behavior. Changes to title rendering can break navigation affordance.

## Observation 7 - View Hub Is a Read-Only Tile Grid

Functional view: View a report presents Prompt, Reports, Matrix, Costs,
Icons, Value view, Rerank, Tournament, Moderation, Fan-out, Fan-in, and
per-meta tiles when data exists.

Source view: `ui/report/view/Main.kt`, `AnswerMatrix.kt`,
`CostViews.kt`, `ValueView.kt`, `Fan.kt`, `FanIn.kt`.

Design implication: View is a derived-content surface. Tiles should
generally read existing report/secondary rows, not start new work.

## Observation 8 - Edit and Regenerate Are a Controlled Mutation Flow

Functional view: users can edit prompt, parameters, system prompt,
models, icons, and titles. Regenerate can rerun changed content or add
newly selected models additively.

Source view: `MetaEditManager`, `RegenerateBatchEngine`,
`ui/report/manage/Edit*.kt`, `regenerate.md`.

Design implication: editing is staged. The user expects changes to be
reviewed before API calls rerun and expects old report history to remain
understandable.

## Observation 9 - Rerank, Meta, and Moderation Are Single-Result
Secondary Tools

Functional view: Rerank produces structured rankings, Meta produces
free-form analysis from user/internal prompts, and Moderation classifies
responses through moderation-capable workers/providers.

Source view: `SecondaryRunManager`, `SecondaryModels.kt`,
`secondary-results.md`, `InternalPrompt` workers category.

Design implication: these tools should be visible as report augmentations
with clear reuse/jump behavior when a result already exists.

## Observation 10 - Fan-Out and Fan-In Create Report-Like Cross-Analysis

Functional view: Fan-out runs one model's answer into another model's
prompt across answerer/source pairs. Fan-in combines those results back
into a synthesized row.

Source view: `FanOutEngine`, `SecondaryRunManager.runFanInPrompt`,
`SecondaryResult` fields `fanOutSourceAgentId` and `fanInOf`,
`secondary-results.md`.

Design implication: these are stored as `META` rows but behave like a
matrix of report-derived content. UI and exports need to group by
structure, not only by kind.

## Observation 11 - Translation Is a Parallel Report Lens

Functional view: translation creates rows per source result and target
language, supports multi-language runs, and feeds translation-specific
views and translator ranking.

Source view: `TranslationRunManager`, `translation.md`,
`ui/report/manage/Translation*.kt`, `SecondaryKind.TRANSLATE`.

Design implication: language is part of report viewing state. Report
content, meta content, titles, icons, and translator ranking can all
depend on target language.

## Observation 12 - Tournament, Judges, Compare, and TransRank Are
Grid-Shaped Analyses

Functional view: these tools run many judged cells, persist match/cell
rows, and sometimes produce aggregate rows. They compare answers,
judges, meta similarity, or translations.

Source view: `TournamentEngine`, `JudgeEvalEngine`, `CompareEngine`,
`TranslatorRankEngine`, `BatchEngine`,
`tournament-judges-compare.md`, `rank-translators.md`.

Design implication: they require batch controls, throttling, hot running
state, recovery, partial progress display, and cell-level persistence.

## Observation 13 - Matrix, Costs, Icons, and Value View Are Local
Derivations

Functional view: Answer matrix, Costs, Icons, and Value view translate
stored report/secondary data into read-only comparisons and summaries.
They should open quickly and avoid API work.

Source view: `AnswerMatrix.kt`, cost view files, `Icons` view,
`ValueView.kt`, `value-view.md`, `costs.md`.

Design implication: correctness comes from stable interpretation of
stored rows. These screens are where data-model ambiguity becomes user
visible.

## Observation 14 - Report Exports Are a Major Functional Contract

Functional view: reports and secondary data can be exported to HTML,
zipped HTML, markdown-derived formats, PDF, DOCX/ODT, JSON traces, and
bulk bundles.

Source view: `ui/helpers/ReportExport.kt`, `ZippedHtmlExport.kt`,
`WordOdtExport.kt`, `ReportStorage` bundle code, report export tests.

Design implication: adding report data is incomplete until export,
redaction, naming, cost visibility, and import/bundle behavior are
considered.
